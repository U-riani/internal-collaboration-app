# Web Push — GTEX Collaboration (web only)

Implementation branch: `prod-notification-sound`. No mobile/Flutter code involved.

## Capabilities

- Browser background notifications for Messages, Tasks (including deadline alerts),
  Approvals, and System events generated by the existing notification service.
- Works with compatible desktop browsers, Android browsers, and iOS 16.4+
  **Home Screen web apps**. iPhone users must first use Safari's
  **Share → Add to Home Screen**, launch from the icon, and then grant permission.
- Clicking a notification opens the linked task, approval, or conversation when
  known; otherwise opens Inbox. An active focused tab suppresses duplicate OS
  notifications. Foreground sound remains controlled by My Account.
- Browser/OS push services provide best-effort delivery, not guaranteed arrival.
  Background notification sound is controlled by the OS/browser, not our custom
  foreground Web Audio sounds.
- Users must opt in separately on each browser/device.
- Only active, non-revoked authenticated sessions receive push. Invalidated
  browser subscriptions are removed after the push service returns HTTP 404/410.
  Sign-out unsubscribes the current browser as well.

## Server preparation

1. Generate a keypair locally, **once per environment**:
   `node apps/api/scripts/generate-vapid-keys.mjs`
2. In the backend server environment, set:
   - `PUSH_VAPID_PUBLIC_KEY` — generated public key
   - `PUSH_VAPID_PRIVATE_KEY` — secret; never commit to Git or expose in web code
   - `PUSH_VAPID_SUBJECT=mailto:your-real-admin-contact@example.com`
   For production Docker Compose, use `.env.production`. API reads all three
   values. Keep the same keypair across deploys to avoid re-subscribing devices.
3. Apply database migrations **to the intended database** before starting:
   `npm --prefix apps/api run db:deploy`
   This adds the `PushSubscription` table with cascading user/session foreign keys.
   Existing data is unaffected. Docker startup may run migrations automatically;
   inspect your deployment procedure before running the command twice.
4. Rebuild/restart the API and web images after deployment.
5. Open My Account → Desktop & mobile push notifications and select Enable.
   Permission is requested only following a user click/tap.

## Local development

- `http://localhost:5173` counts as a secure context in current browsers.
  A LAN IP address over HTTP generally does **not** support Web Push; use HTTPS
  when testing on a physical Android/iPhone.
- `GET /api/v1/push/config` returns `enabled:false` until all three
  server-side VAPID variables are configured.
- The push endpoint allowlist includes FCM (Chrome/Android),
  Mozilla autopush (Firefox), Apple Push (Safari iOS Home Screen),
  and Windows notification service endpoints (Edge). Extend the allowlist if
  a browser's legitimate gateway changes in the future.
- No scheduled polling, third-party push SDK, or Firebase project is required.
  Push payloads are encrypted with RFC 8291 aes128gcm and authenticated with
  RFC 8292 VAPID (ES256).
- Do not use production PostgreSQL or VAPID private keys in local development.
